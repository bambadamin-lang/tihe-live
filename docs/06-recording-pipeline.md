# Recording Pipeline — the Live ↔ VOD Contract

**This is the interface between the two developers.** It is specified before either side is
built so both can work in parallel. Changes here need agreement from both owners.

The contract has exactly three parts: a **bucket layout**, a **webhook**, and a **class
metadata row**. Nothing else crosses the boundary — the video pipeline never calls into
`services/live`, and `services/live` never touches `videos` or `video_assets`.

---

## Part 1 — Bucket layout (`services/live` writes, `ingest-worker` reads)

LiveKit Egress must be configured to write room composite output here:

```
s3://tihe-raw/recordings/{classId}/{sessionId}/
    composite.mp4          # room composite, H.264 + AAC — the primary artifact
    metadata.json          # written by services/live, see below
```

`classId` and `sessionId` are ULIDs generated by `services/live`. `sessionId` is unique per
*occurrence* of a class, so a weekly class has one `classId` and many `sessionId`s. The
LiveKit room is named after the `sessionId`, so `livekitRoom` below is the session id.

The composite is rendered by `services/live/egress-template` — the class layout without the
chat, participant and hand pods, so no student names end up in a library video
([11-live-classroom.md](11-live-classroom.md) §10). Egress cannot pause, and a restarted egress
would overwrite `composite.mp4`, so v1 records each session as one continuous file.

`metadata.json`, written by `services/live` **before or at egress start**:

```jsonc
{
  "classId": "cls_01J8Z...",
  "sessionId": "ses_01J8Z...",
  "courseId": "crs_01J8Z...",        // which course this class belongs to — required
  "sectionId": "sec_01J8Z...",       // optional: which section/week to file it under
  "title": "جلسه ۴ — مشتق توابع مرکب",
  "teacherId": "usr_01J8Z...",
  "scheduledStartAt": "2026-09-27T08:00:00Z",
  "actualStartAt":    "2026-09-27T08:04:12Z",
  "actualEndAt":      "2026-09-27T09:38:50Z",
  "participantCount": 43,
  "livekitRoom": "ses_01J8Z...",
  "egressIds": ["EG_abc123"]
}
```

`services/live` writes `metadata.json` at egress start, and **rewrites it with `actualEndAt`
and `participantCount` before it calls `stopEgress`** — so by the time `egress_ended` fires,
the file ingest reads is final.

`courseId` is the one field the pipeline cannot work without — it decides who can see the
resulting video. If it is missing, the recording lands in `needs_attention` for manual filing
rather than being published to the wrong audience.

## Part 2 — Webhook (`LiveKit` → `services/api`)

LiveKit is configured with a webhook pointing at:

```
POST https://api.tihe.local/webhooks/livekit
Authorization: <LiveKit JWT, verified against LIVEKIT_API_SECRET>
```

The API verifies the signature, then handles `egress_ended`:

```jsonc
{
  "event": "egress_ended",
  "egressInfo": {
    "egressId": "EG_abc123",
    "roomName": "ses_01J8Z...",
    "status": "EGRESS_COMPLETE",
    "startedAt": 1759046652000000000,
    "endedAt":   1759052330000000000,
    "fileResults": [{
      "filename": "recordings/cls_01J8Z.../ses_01J8Z.../composite.mp4",
      "location": "s3://tihe-raw/recordings/cls_01J8Z.../ses_01J8Z.../composite.mp4",
      "size": 1843200000,
      "duration": 5678000000000
    }]
  }
}
```

Other events (`egress_started`, `egress_updated`, `room_finished`) are accepted and logged but
trigger no pipeline work. Unknown events return `200` and are logged — never `400`, or LiveKit
will retry forever.

**Idempotency.** LiveKit retries webhooks. The handler upserts on `egressId`, so a duplicate
delivery does not create a second `recordings` row or a second job.

**Failure statuses.** `EGRESS_FAILED` or `EGRESS_ABORTED` creates the `recordings` row with
`status: failed` and the error text, so a lost recording is visible rather than silently
absent. This matters: a class that was not recorded needs a human to know.

## Part 3 — Processing states

`recordings.status` progresses:

```
pending ──► ingesting ──► packaging ──► ready
   │            │             │
   │            └─────────────┴──► failed          (retryable, error recorded)
   └──► needs_attention                            (missing courseId, zero-length file)
```

Job chain, both on BullMQ:

| Queue | Job | Does |
|---|---|---|
| `ingest` | `ingest:process` | Fetch `metadata.json`, validate the MP4 (duration > 0, has a video track), remux to a clean faststart MP4, create the `videos` row as `processing`, enqueue packaging. |
| `media` | `media:package` | Rendition ladder, poster, thumbnail sprite, CEK generation, AES-CTR encryption, HLS packaging, upload to `tihe-vod`, write `video_assets` + `content_keys`, set `videos.status = ready`. |

Both jobs are idempotent: keyed on `recordingId`, they check for existing output before doing
work, so a retry after a crash resumes rather than duplicating.

**Retention.** After `ready`, the raw `composite.mp4` is deleted following
`RAW_RETENTION_DAYS` (default 7). Keeping an unencrypted master in object storage
indefinitely undoes the encryption work.

## Output layout (`tihe-vod`)

```
s3://tihe-vod/{videoId}/
    master.m3u8               # multi-variant playlist
    1080p/index.m3u8  seg-00000.ts ...   # AES-128-CTR encrypted segments
    720p/ ...  480p/ ...  audio/ ...
    poster.jpg
    sprite.jpg  sprite.vtt    # thumbnail scrubbing
```

Segments are encrypted **before** upload. The manifests contain no `#EXT-X-KEY` line — the key
never travels with the media. `secure-core` rewrites the manifest for the local player.

---

## What each developer can build without the other

Because the contract is a bucket layout plus a webhook:

- **The live-classroom session** can develop `services/live` against a real MinIO and verify egress output
  lands correctly, without the pipeline existing. A `metadata.json` written by hand proves the
  format.
- **The video session** can develop the pipeline by dropping an MP4 and a `metadata.json` into `tihe-raw`
  and POSTing a fake `egress_ended` payload to the webhook, without LiveKit running at all.
  `infra/scripts/fake-egress.sh` does exactly this.

Neither of you is ever blocked on the other.
